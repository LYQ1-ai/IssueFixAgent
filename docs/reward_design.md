# Repo 根因定位 Agent 的 Reward 设计（综合方案）

> 本文档综合 GLM 5.3 MAX / Gemini 3.7 Flash / Consensus 三家调研结论，结合本项目
> （CodeAgentRL 阶段 1：MCTS 数据生成）的**实际数据与真实 rollout 验证**，给出综合
> 方案（第一部分）；三家的原始方案原文附于文末（第二部分），供追溯与对照。
>
> 综合方案的三个共识来源：① 三家一致同意废弃"三层独立 F1 相加"（冗余计分、粒度无区分）；
> ② 层级路径部分匹配 + 一对一最大权匹配 + Soft-F1；③ 粒度缺失折算与过度预测惩罚。

## 第一部分：综合方案（主基调）

### 1. 问题诊断（为什么现有"三层独立 F1 相加"要改）

现有评分 `reward = F1_file + F1_module + F1_entity ∈ [0,3]` 有三个结构性缺陷：

1. **冗余计分**：一次 func 级命中（`file:Class.method`）会同时抬升 file / module / entity
   三层 F1（三层共享同一命中），正确信息被重复计入约 3 次；
2. **粒度无区分**：三层各 +1 的边际贡献相同，`f` 与 `f:c.m` 的差距只有 1.0/3.0；经阈值
   二值化后 file-only 与 full 定位的 rollout 判定可以完全相同，RL 缺乏向细粒度细化的压力；
3. **防刷分弱**：冗余预测（同时报 `{f}` 和 `{f:c}`）不损失任何分数，多报位置不受惩罚。

数据事实（39,284 实例，见 §6）：91% 单文件、98% 位置为 entity 级、位置数 1 的占 75.5% ——
文件级命中几乎白送，真正的判别信号在 class → func 的细化上；同时 24.5% 实例多位置、长尾
有几十上百位置，集合级匹配是刚需。

### 2. 设计思路（一句话）

**把 `file / class / func` 从"三个独立 F1 任务"改为"同一条根因路径的不同完成深度"：
每个位置只按最深正确层级计一次分，预测与 gold 做一对一最大权匹配，聚合为 Soft-F1 连续
奖励，再以语义化阈值二值化供 MCTS 门控使用。**

要点拆解：

- **位置 = 路径三元组** `(file, class, func)`，缺失层记为 ⊥（gold 缺失层按最细可得粒度
  折算，保证缺失实例可达满分，不系统性压分）；
- **只计最深命中**：匹配深度 d ∈ {0,1,2,3}，得分 `s(d)` 严格递增（默认 `s(1)=0.2,
  s(2)=0.5, s(3)=1.0`），粒度 ⇒ reward 档位硬上限（纯 file 策略上限 0.2，纯 class 上限 0.5）；
- **一对一最大权匹配**：每个预测最多匹配一个 gold、每个 gold 最多被匹配一次（深→浅贪心，
  等价匈牙利最优），杜绝"一个粗预测蹭多个 gold / 重复预测刷同一 gold"；
- **Soft-F1 聚合**：`Reward = 2C / (M+N) ∈ [0,1]`（C = 匹配总折算分，M/N = 预测/gold
  位置数）—— 同时惩罚漏报（recall）与过度预测（precision），闭式与
  `2·P·R/(P+R)`（P=C/M, R=C/N）恒等；
- **连续奖励 + 二值门控双轨**：连续 Soft-F1 直接作为 PRM 连续标签来源；二值化
  `correct = Reward ≥ τ` 只服务于 MCTS 门控（`0<MC<1`）与二分定位，二者解耦。

### 3. 可调整超参数

| 参数 | 默认 | 说明 |
| --- | --- | --- |
| `depth_weights` | `{1: 0.2, 2: 0.5, 3: 1.0}` | 各匹配深度的得分；单调递增，func 档必须显著高于 file 档 |
| `reward_threshold`（τ） | `0.6` | correct 阈值；应落在 class 档(0.5)与 func 档(1.0)之间 ⇒ "正确 = 至少精确定位到函数级" |
| `missing_level_norm` | `true` | gold 层级缺失（L<3）时按该位置最细可得层级 Lᵢ 折算 credit，缺失实例可达满分 |
| `strict_multi_gate` | `true` | N≥2 时额外硬条件：func 级命中数 ≥ ⌈N/2⌉，防多文件实例靠 file 级堆 recall 混过 |
| `overpromise_penalty`（δ） | `0.0` | 断言了 func/class 但未命中的每个多余层级扣 δ（校准粒度自信度；δ 从 0 起步） |
| `duplicate_penalty` | `0.0` | 相同 file / (file,class) 前缀的未匹配冗余预测每项扣分（提示词已禁重复条目，默认关） |
| `reward_mode` | `"layered"` | `"layered"`（本方案）/ `"independent"`（旧三层 F1 求和，保留作对照） |
| `f_beta` | `1.0` | F1 变体 β：`R = (1+β²)C/(β²M+N)`；β=0.5 更重 precision（观测到广撒网时启用） |

校准基线（oracle）：file-only / class-only / full 在 M=N 时应分别得 ≈0.2 / 0.5 / 1.0，
random ≈ 0 —— 用此三档校验实现正确性。

### 4. 计算流程（伪代码）

```
输入：submission = submit_locations 的 locations JSON
      gold       = 实例的 file_changes（→ 三元组集合）

1. 归一化
   preds = [(f, c, fn) for loc in locations]           # 缺失层 = None
   golds = triples_from_file_changes(file_changes)     # 与 codescout 抽取同口径
   规范化路径（去 ./、/ 前缀、统一大小写）；preds / golds 各自去重

2. 匹配深度 match_depth(p, g)：
   ┌──────────────┬────────────────────────────────────────────┬────────┐
   │ gold 结构     │ 条件                                        │ d      │
   ├──────────────┼────────────────────────────────────────────┼────────┤
   │ 任意          │ p.file ≠ g.file                            │ 0      │
   │ 有 class      │ p.class ≠ g.class（或未给）                 │ 1      │
   │ 有 class      │ class 同；gold 有 func：p.func==g.func→3 / 错→2 │ 2/3    │
   │ 有 class      │ class 同；gold 无 func（最细即 class）        │ 2      │
   │ 无 class 有 func │ p.func == g.func → 3；否则 → 1           │ 1/3    │
   │ 无 class 无 func │ —                                        │ 1      │
   └──────────────┴────────────────────────────────────────────┴────────┘

3. 一对一最大权匹配
   候选 = {(pᵢ, gⱼ) : d>0, score = s(d)}，按 score 降序贪心选取，
   每个 p / g 至多使用一次（等价匈牙利最优匹配）

4. 聚合（含缺失折算）
   Lⱼ = gold gⱼ 的最细可得层级（有 func→3，有 class→2，否则 1）
   C  = Σ_matched s(d) / s(Lⱼ)        # 缺失实例的匹配对也可拿到满分 credit
   M, N = len(preds), len(golds)
   Reward = 2C / (M + N)              # ∈ [0, 1]

5. 二值化（MCTS 门控 / 二分定位用）
   correct = (Reward ≥ τ)
   若 strict_multi_gate 且 N ≥ 2：correct &= (#(d==3) ≥ ⌈N/2⌉)
```

### 6. 真实数据验证（gemma-4 10 树 demo，565 条 rollout 离线重打分）

用 `outputs/mcts_gemma` 的真实 submission 重算（§4 流程）：

- **深度分布**：根 rollout 匹配深度 `{d=3: 40, d=1: 20, d=2: 0}` —— 模型行为天然二态
  （要么函数级全中、要么只对文件），几乎不出现"类对函数错"的中间态；
- **τ 敏感性**：τ=0.5/0.6/0.7 的 correct_rate = 0.559/0.542/0.513，门控树数恒为 4/11 ——
  τ∈(0.2,1.0) 内行为稳定，0.6 的精确取值不影响当前数据判定；
- **权重敏感性**：三家权重（0.2/0.5/1.0、0.35/0.70/1.0、0.3/0.6/1.0）correct 完全相同
  （0.559）—— 权重档在二态数据上等价，无需过度纠结，默认取 0.2/0.5/1.0；
- **与旧方案行为兼容**：旧独立求和 θ=2.0（correct 55%、门控 4/10）与新方案 τ=0.6
  （correct 54.2%、门控 4/11）几乎一致 —— 重写不破坏现有管道，但修复了结构性缺陷
  （在出现 d=2 中间态、多位置、冗余预测时才会体现差异）。

## 第二部分：原始各家方案（调研原文）

### GLM 5.3 MAX 提出的方案

# Repo 根因定位 Agent 的 Reward 机制设计

## 一、现有方案的问题诊断

当前"三级 F1 独立计算再相加"的方案，其两个缺陷有共同根源——**计分粒度与预测粒度没有对齐**：

1. **冗余计分**：一次 func 级命中会同时抬升 file/class/func 三条 F1，粗粒度信息被重复计入约 3 次，reward 量纲失真；
2. **粒度无区分**：F1 相加后每个粒度档的边际贡献相同（file→class 与 class→func 各 +1），再经阈值二值化后，只要阈值设得能让粗粒度过线，file-only 与 full-prediction 的 rollout 判定完全相同，RL 没有任何向细粒度细化的压力。

数据事实进一步约束设计：**91% 单文件**意味着 file 级是低信息量、近乎二值的粗筛（reward 质量应压在 class/func 级）；9% 多文件实例需按 location 逐条处理；约 1.5%–2% 的层级缺失需通配兼容。

## 二、核心机制：最细粒度单遍匹配 + 阶梯计分 + 加权 F1

### Step 1：预处理与归一化
- 将 gt 与预测均解析为三元组 (file, class, func)，缺失层记为 ⊥；路径做规范化（去 repo 前缀、统一大小写）；gt 与预测各自去重。
- 为每个 gt location 确定其**最细可用层级** Lᵢ（func 缺失则 L=class，依此类推），缺失层在匹配时视为通配。

### Step 2：计算匹配深度
对每个（预测， gt）对计算匹配深度 d：

- **d=3**：file ∧ class ∧ func 全中；
- **d=2**：file ∧ class 中（func 错或未给出）；
- **d=1**：仅 file 中；
- **d=0**：未中。深度上限不超过 Lᵢ。

### Step 3：一对一最优匹配，每个匹配对只计一次分
按深度从深到浅贪心完成预测与 gt 的一对一匹配（99% 实例 N≤2，计算代价可忽略；必要时可用匈牙利算法求精确最优）。每个匹配对的得分为：

**credit = s(d) / s(Lᵢ)**，其中阶梯权重 **s(func)=1.0，s(class)=α=0.5，s(file)=β=0.2，s(∅)=0**

除以 s(Lᵢ) 是为了让层级缺失的 gt location 也能拿到满分（归一到该 location 的最细可得粒度）。

### Step 4：聚合成有界 Reward
记 C = 所有匹配对 credit 之和，则加权精确率 P=C/M、加权召回 R=C/N，二者合并后得到极简闭式：

**Reward = F1(P, R) = 2C / (M + N) ∈ [0, 1]**

### Step 5：有效判定（双层 Gate）
- 连续阈值：**R ≥ τ，推荐 τ = 0.6**（落在 α 与 1 之间）；
- 语义硬条件（N≥2 时）：**最细粒度（func 级）命中数 ≥ ⌈N/2⌉**，即"过半根因被精确钉死"。

## 三、该机制的关键性质（直接回应两个痛点）

| 性质 | 说明 |
| --- | --- |
| **无冗余** | 每个（预测， gt）对只在其**最细匹配深度**计一次分，file 不再被三级各算一遍 |
| **粒度严格区分（档位上限）** | 可证明：纯 file 策略的 R 上界恰为 β=0.2，纯 class 策略上界恰为 α=0.5，只有真实 func 命中才可能逼近 1。**粒度 ⇒ reward 硬上限**，阈值判定天然区分粒度 |
| **防刷分** | R=2C/(M+N)：多报、错报、重复刷同一文件都会稀释精度；重复报同一 file 封顶在 β |
| **单调性** | 正确方向上细化粒度、或删掉错误预测，reward 严格不降——RL 梯度方向正确 |
| **全实例可达满分** | 按 Lᵢ 折算后，层级缺失实例不被系统性压分；每个实例满分恒为 1 |
| **课程效应** | file 命中给 β 的保底信号可供早期学习，终端优化压力集中在 func 定位 |

## 四、示例（gt = 1 个 location：f:c:u，τ=0.6）

| Agent 预测 | C | Reward | 判定 |
| --- | --- | --- | --- |
| f:c:u | 1.0 | 1.0 | 有效 |
| f:c（只到 class） | 0.5 | 0.5 | 无效 |
| f（只到 file） | 0.2 | 0.2 | 无效 |
| f:c:u′（class 对 func 错） | 0.5（−δ） | 0.5 | 无效 |
| [f:c:u, 另一个错的] | 1.0 | 0.67 | 有效 |
| [f:c:u′, f:c:u″] | 0.5 | 0.33 | 无效 |

多文件例：gt 两处，预测 1 个全中 + 1 个 file 命中 → C=1.2，R=2×1.2/4=0.6，恰好压线（若要求更严可设 τ=0.65）。

## 五、针对数据集特征的适配

1. **91% 单文件**：reward 退化为干净的三档阶梯分；file 档低权重（0.2）避免训练早期在"找对文件"上饱和，差异化信号集中在 class→func 的细化上。
2. **9% 多文件**：逐 location 归一 + 集合匹配天然支持；建议训练时对多文件实例做实例级加权（如 1+log₂N）或分层采样，防止跨文件根因模式被淹没。
3. **层级缺失（≤2%）**：通配匹配 + credit 上限折算，不产生永远拿不到满分的实例。

## 六、参数校准与使用建议

- **用三个 oracle 基线校准**：file-only oracle、class-only oracle、full oracle 在 M=N 时应分别得 ≈β、α、1，random≈0。τ 应设在"你要求的最粗有效档"与下一档之间——设 τ∈(α,1) 即"有效 = 至少精确定位到函数级"。
- **RL 使用方式**：建议直接以连续 R 作为 reward（信号稠密、档位上限保证区分度），阈值 gate 仅用于 rollout 过滤或课程控制；**不要把二值有效性当作唯一 reward**——这正是当前设计粒度无区分的根源之一。
- **可选项**：
  - 更重召回（宁可多报根因）：改用 F₂，即 R=5C/(4N+M)，档位上限性质不变；
  - **过度承诺惩罚 δ≈0.05**：对"断言了 func/class 但未命中"的每个多余层级扣分，校准 Agent 的粒度自信度（防止 bluff 细粒度），但 δ 过大会压制探索，建议从 0 或极小值起步；
  - 监控 M 的分布（是否坍缩为恒报 1 个）、各档命中率、gate 通过率，防止利用常见函数名（init/main 等）刷分。

## 七、备选等价视角（供参考）

也可用**边际分解**消除冗余：R = β·Acc_file + (α−β)·Acc_class|file + (1−α)·Acc_func|class，即每级只对"上一级正确前提下"的细化增益计分。该形式在单文件情形与上述方案等价，但在多位置、M≠N 时边界情况繁琐；统一采用"配对最细深度计分"的方案更简洁，且上述各条性质均可直接证明。

### Gemini 3.7 Flash 提出的方案

针对你提到的"file级冗余计算"、"不同粒度Reward相同"以及"91%的实例集中在单文件"等痛点，我为你设计了一套**基于层级衰减与软匹配（Soft Matching）的 Reward 机制**。

这套机制的核心在于：**将一次预测视为一个由粗到细的"路径"（Path），通过对路径深度的加权计算单点匹配度，再通过二分图匹配计算全局的 Soft-F1。** 这样既能消除冗余，又能精确区分粒度，同时利用数据集的高单文件占比特征对"广撒网"的预测行为进行精准惩罚。

---

### 1. 核心得分逻辑：层级权重分配 (Hierarchical Weights)

为了解决"各个级别独立计算导致 file 被重复计算"和"粒度不同 reward 相同"的问题，我们需要设定一个**单调递增且总和为 1 的层级权重**。

假设设定的权重分布为：

* $W_{file} = 0.2$ （定位到文件，贡献基础分）
* $W_{class} = 0.3$ （定位到类，贡献进阶分）
* $W_{func} = 0.5$ （定位到确切函数，贡献核心分）
*(注：由于 entities 覆盖率极高，说明精确到 function 是非常有价值的，因此给予最高权重。)*

**单点匹配度得分 $S(p, g)$ 计算：**
对于 Agent 的任意一个预测 location $p$ 和真实 location $g$，它们的匹配得分 $S(p, g)$ 在 $[0, 1]$ 之间：

1. **File 级不匹配**：直接返回 $0$。
2. **File 级匹配**：获得 $0.2$ 分。
   - **Class 级不匹配**：匹配结束，得分为 $0.2$。
   - **Class 级匹配**：追加 $0.3$ 分（累计 $0.5$）。
     - **Func 级不匹配**：匹配结束，得分为 $0.5$。
     - **Func 级匹配**：追加 $0.5$ 分（累计 $1.0$）。

**机制优势：** 彻底解决了冗余相加的问题。如果 Agent 只预测到了 file，它只能拿到 0.2 分，而精准预测到 func 可以拿到满分 1.0，直接拉开了不同预测粒度的 Reward 差距。

---

### 2. 全局 Reward 计算：基于二分图的 Soft-F1

真实情况 GT 中有 $N$ 个 location，Agent 预测了 $M$ 个 location。为了防止 Agent 输出的大量 location 被重复计分，我们需要计算二者的**最大匹配总分**。

**步骤 1：构建得分矩阵与最优分配**
计算出一个 $M \times N$ 的得分矩阵，然后使用匈牙利算法（Hungarian Algorithm）找出最大加权匹配，确保每个预测 location 最多只能匹配一个 GT location，反之亦然。
令匹配后成功配对的边集合为 $E$，单对边的得分为 $S_i$。

**步骤 2：计算 Soft-Precision 和 Soft-Recall**
由于得分在 $[0,1]$ 之间，我们可以引入"软"准确率和召回率：

$$Soft\_Precision = \frac{\sum_{i \in E} S_i}{M}$$
$$Soft\_Recall = \frac{\sum_{i \in E} S_i}{N}$$

**步骤 3：计算基础 Reward (Soft-F1)**

$$Reward_{base} = 2 \times \frac{Soft\_Precision \times Soft\_Recall}{Soft\_Precision + Soft\_Recall}$$

---

### 3. 结合数据集特征（91% 实例单文件）的针对性惩罚

根据你提供的数据事实：**91.0% 的 GT 只有 1 个文件，大于 2 个文件的仅占 1.1%**。这意味着如果 Agent 输出包含了大量的文件位置，大概率是在"广撒网"凑 Recall。为了训练出一个高精度的 Agent，必须对过度预测（$M \gg N$）进行严厉惩罚。

**设计方案 A：使用 $F_{\beta}$ 替代 F1 (推荐 $\beta = 0.5$)**
F1 将 Precision 和 Recall 视为同等重要，但在这种极端长尾分布下，Agent 输出 5 个文件命中 1 个的代价应该远高于漏掉 1 个。使用 $F_{0.5}$ 会给 Precision 赋予两倍于 Recall 的权重，迫使 Agent 变得更"谨慎"。

$$Reward_{F0.5} = (1 + 0.5^2) \times \frac{Soft\_Precision \times Soft\_Recall}{(0.5^2 \times Soft\_Precision) + Soft\_Recall}$$

**设计方案 B：硬性数量惩罚（Length Penalty / Over-prediction Penalty）**
既然超过 2 个文件的 GT 只有 1.1%，我们可以直接对预测数量 $M$ 施加阈值截断或指数衰减：

$$Penalty = \begin{cases} 1.0, & M \le 2 \\ e^{-\alpha (M-2)}, & M > 2 \end{cases}$$

最终的 $Reward = Reward_{base} \times Penalty$。（其中 $\alpha$ 可以设置为 0.2 或 0.5）。这样，即使 Agent 侥幸命中了所有根因，但如果它提交了 10 个 location，奖励也会被大打折扣。

### Consensus 给出的方案

# **Repo 根因定位** Reward 设计

现有设计不合理；更合适的做法是把 `file → class → func` 视为**单个层级路径上的部分匹配问题**，先做**一对一匹配**避免重复计分，再用**递进式层级得分**给部分命中以不同信用，最后再加一个**轻量的有效 rollout 门槛**，而不是把三个层级的 F1 直接相加。

## 设计原则

你的任务本质上是**集合预测**而不是单标签分类：一个 issue 对应 `N` 个 gt locations，agent 输出 `M` 个预测 locations，而过多输出会增加噪声和后续处理成本，所以 reward 必须同时奖励覆盖率并惩罚过预测。

直接在 file、class、func 三层各算一次 F1 会产生**重复奖励**，因为同一个正确 file 会在更细粒度层再次被"算中"；类似问题在多层标注和 span 评测中已知会造成 double penalty 或 double counting，因此更公平的做法是让每个预测和每个 gt **只参与一次匹配与计分**。

层级任务的关键信号不是"有没有碰到某层"，而是**命中了多深**。分层 RL 和 hierarchical credit assignment 的共同结论是，粗到细的信用分配比单一终局分数更稳定，也更能反映真实贡献。

## 推荐 Reward 结构

建议把每个 location 统一表示为一条路径：`(file, class, func)`。对每个预测 `p` 和 gt `g` 定义**层级相似度**，但只按"最深正确层级"计一次分：

| 匹配结果 | 单对得分 |
|---|---:|
| file 不同 | 0 |
| file 相同，class 不同 | 0.35 |
| file、class 相同，func 不同/缺失 | 0.70 |
| file、class、func 全相同 | 1.00 |

这个分值结构体现"越深越值钱"，同时避免 file 命中在 class 和 func 再被重复加分。之所以采用**非线性递增**而不是 `1/3, 2/3, 1`，是因为你的数据 91% 为单文件实例，若 file 命中给分过高，模型会倾向停在 file 粒度，学不到更细定位。

然后在一个 issue 内，对预测集合与 gt 集合做**最大权一对一匹配**。也就是每个预测最多匹配一个 gt，每个 gt 也最多匹配一个预测，目标是让全局总得分最大。这和多 span / 多实体 / 多目标评测中常见的 set-based matching 思想一致，本质作用就是防止一个粗粒度预测"蹭中"多个 gt，或多个重复预测反复吃到同一个 gt 的分数。

## Issue 级公式

在完成一对一匹配后，令所有匹配对的层级得分之和为 `C`。定义：

| 指标 | 公式 | 含义 |
|---|---|---|
| Soft Precision | `C / M` | 预测里有多少"有用" |
| Soft Recall | `C / N` | gt 被覆盖了多少 |
| Soft F1 | `2PR / (P+R)` | 综合主分 |
| Exact Hit Rate | `#完整命中 / N` | 完整定位比例 |

主 reward 建议使用：

`Reward = 0.8 * SoftF1 + 0.2 * ExactHitRate`

这样做有三个好处。第一，SoftF1 保留了集合预测中 precision-recall 的平衡，适合 `N ≠ M` 的情形。第二，ExactHitRate 明确拉开"只到 file/class"与"完整命中 func"的差距，解决你现在不同粒度 reward 接近的问题。第三，主分仍是连续值，适合 RL 优化，而不是纯二元信号。

## 数据集偏态下的校准

由于 91.0% 的实例只有 1 个 gt file，reward 若不校准，会天然偏向"猜一个文件就够了"。因此建议把 reward 分成**主通道**和**多文件修正通道**。

主通道对所有样本统一使用上面的 SoftF1 + ExactHitRate。多文件修正通道只在 `N_file > 1` 时启用，额外加入一个 **file coverage bonus**，例如：

`MultiFileBonus = 0.1 * FileRecall`

最终：

`FinalReward = BaseReward + I(N_file>1) * MultiFileBonus`

同时，不建议把 file 级奖励权重再调高。你们的数据里 file 本就容易命中，真正稀缺的是更细粒度的 entity 级定位。

## 冗余预测与无效 rollout

为了抑制 agent 通过"多报一些位置"刷 recall，建议加入**重复与冗余惩罚**。如果多个预测拥有相同 file、或相同 `(file,class)` 前缀，但只有一个最终匹配，其余未匹配项应承担小额惩罚，例如每个 `-0.05`。

还应加入**空梯度/无信息 rollout 过滤**。GRPO 类方法在组内 reward 方差为零时不给有效梯度，很多 rollout 只是消耗算力；因此"是否有效"最好依据**相对质量差异**和**最小语义命中**，而不是一个生硬的三层 F1 总和阈值。

建议把 rollout validity 设成两段式：

| 条件 | 作用 |
|---|---|
| `BaseReward ≥ τ1` | 连续质量下限 |
| 或 `至少1个匹配对得分 ≥ 0.70` | 至少命中到 class/func 级 |

可取 `τ1` 为较低值，如 0.25–0.35，对应"不是乱猜"；第二条确保真正有局部正确的 rollout 不会因集合规模波动被误杀。

## 实际落地建议

| 模块 | 建议 |
|---|---|
| 基本对象 | 以 `(file,class,func)` 路径作为唯一 location 单元 |
| 匹配方式 | 预测集与 gt 集做最大权一对一匹配 |
| 单对得分 | 0 / 0.35 / 0.70 / 1.00 |
| 主 reward | `0.8*SoftF1 + 0.2*ExactHitRate` |
| 多文件修正 | `N_file>1` 时加 `0.1*FileRecall` |
| 冗余惩罚 | 每个未匹配重复前缀预测减小额分数 |
| rollout 有效性 | `BaseReward` 阈值或存在高质量匹配对 |

如果 agent 输出本身带置信度，还可以把上面的 precision/recall 扩展成**置信度加权**版本，因为概率化 F1 比硬阈值 F1 对排序质量更敏感，也更适合训练信号。

若未来 agent 改成先找 file、再找 class、最后找 func 的显式多步策略，那么训练层面还可把 reward 进一步拆成 turn-level 或 hierarchical advantage 信号，让粗粒度命中先提供信用、细粒度命中再加码。

结论上，最合理的机制不是"三层 F1 相加"，而是**层级部分匹配 + 一对一集合匹配 + 精确命中附加奖励 + 轻量有效性门槛**。这里最重要的变化是：把 `file/class/func` 从三个独立任务改成**同一 root-cause path 的不同完成深度**；最大的开放问题则是单对层级分值的最优校准，应最终用训练集上的 repair success 或人工偏好做标定。
